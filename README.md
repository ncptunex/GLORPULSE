# GLORPULSE

> **Your health, monitored beyond Earth.**

GLORPULSE is a browser-based health-monitoring prototype for astronauts on a simulated long-duration Mars transit. It records daily health readings, compares each astronaut with **their own baseline**, and explains in plain language what changed, how it compares with that astronaut's normal, and what the app can and cannot say about it.

Built for the **NASA Space Apps Challenge 2026** (Kuala Lumpur), challenge: *Health Monitoring Software for Astronauts*.

> **All data in GLORPULSE is simulated.** It is a decision-support prototype, not a medical device.

## The Problem

NASA's Human Research Program groups the health risks of spaceflight into five hazards: space radiation, isolation and confinement, distance from Earth, gravity (and the lack of it), and hostile or closed environments.

Distance from Earth is the hazard that motivates GLORPULSE most. Medical care, instructions and supplies become harder to receive from Earth the further a crew travels. NASA states that the one-way communication delay between Earth and Mars is approximately **4 to 24 minutes**, depending on how far apart the planets are. NASA's Exploration Medical Capability work also describes Mars-class missions where emergency evacuation and terrestrial medical assistance are not available.

That means astronauts may need to notice and assess changes in their own health, and most are not doctors. A reading with a coloured dot says something is off, but it does not say:

- how the reading compares with *that person's* normal,
- why it might matter in space, or
- where the guidance comes from.

## Our Solution

GLORPULSE closes that gap in three steps:

1. **Compare each astronaut with themselves.** The app builds a personal baseline from the astronaut's own first seven days of readings, then checks whether later readings stay away from it.
2. **Explain every alert.** Each alert opens a six-part "Why Now" explanation in plain language.
3. **Be honest about evidence.** Every medical statement must carry a verified source ID. If there is no source, the app says **"No sourced guidance available"** instead of inventing advice.

The health logic is kept separate from the user interface, so the screens only display what the logic returns.

## Key Features

| Feature | What it does |
|---|---|
| **Astronaut profiles** | Four simulated astronauts, switched with a selector. No login. Each astronaut's readings, baselines, alerts and explanations are kept separate and never mixed. |
| **Health indicators** | Heart rate, blood pressure (systolic and diastolic), body temperature, sleep, mood (a non-diagnostic 1 to 5 self-rating), and blood glucose for astronauts where it applies. |
| **Personal baselines** | The baseline is the median of an astronaut's first 7 days of readings for an indicator, with a spread based on the median absolute deviation. Until 7 days exist, the indicator card shows "Baseline: N of 7 days" and no deviation or alert is claimed. |
| **Deviation and persistence** | A reading *deviates* when it is far enough from the baseline centre (prototype setting K = 3). The app counts how many days in a row the deviation has lasted in the same direction. Three or more days is *sustained*. A missing day ends a run. |
| **Alert levels** | **Info**, **Watch** and **Action** are generated by simple, visible prototype rules, and each alert shows the rule that triggered it. A fourth level, **Contact Flight Surgeon**, appears in the legend only (see [Safety and Limitations](#safety-and-limitations)). |
| **Why Now explanations** | Six parts per alert: what changed, comparison with the astronaut's baseline, why it may matter in spaceflight, relevant NASA hazards, next steps, and when to contact the flight surgeon. Parts 3 to 5 come only from sourced guidance. **No sourced guidance has been added yet**, so at present those parts collapse into one note reading "No sourced guidance available for this alert", and parts 1, 2 and 6 carry the explanation. |
| **Health check-ins** | A form for the active astronaut's current mission day (day 30 in the demo), with entry limits that reject typing errors and a short placeholder symptom list. A later entry for the same indicator on the same day replaces the earlier one. |
| **Charts** | One time-series chart per indicator with the astronaut's baseline band, gaps for missing days, and a table alternative for screen readers. |
| **Body figure** | An optional clickable body figure that links regions to the indicators they relate to. Sourced text is shown only where it exists, and currently every region reads "No sourced guidance available". |
| **Source transparency** | Reference status reads **Not assessed** wherever no verified reference range exists. Baseline, general reference range and mission limit are kept separate and never merged. |
| **Accessibility** | Status uses text and icons, not colour alone. A skip link and native buttons and form controls are used. WCAG 2.2 AA is an aim and has not been formally tested. |
| **Persistence and reset** | Entered check-ins are saved in the browser's `localStorage` per astronaut. The footer button (with a confirmation) deletes all entered check-ins. The seeded data is built into the code and is unaffected. |

### Not implemented

These appear in the planning documents but are **not** in the current app:

- The **Flight Surgeon Briefing**, simulated communication-link toggle and outbox.
- Streaks, environment modes, data-confidence tips and briefing export.
- Any real transmission of health data. The app makes no network requests for health data.

## Technology Stack

| Area | Technology |
|---|---|
| UI | [React](https://react.dev/) 19 |
| Language | [TypeScript](https://www.typescriptlang.org/) 6 |
| Build tool | [Vite](https://vite.dev/) 8 with `@vitejs/plugin-react` |
| Charts | [Recharts](https://recharts.org/) 3 |
| Styling | Plain CSS (`src/styles/global.css`) |
| Storage | Browser `localStorage` |
| Tests | [Vitest](https://vitest.dev/) 5 (health-logic and data tests, run in Node). There are no component or browser tests |

There is **no backend, no cloud database, no user accounts, no machine learning and no real-time or wearable data**. Everything runs in the browser.

The key design rule: **`src/logic` never touches the screen or `localStorage`**, and the UI never calculates statuses or alerts. Derived results (baselines, alerts and so on) are recalculated from stored readings every time and are never saved.

## Getting Started

### Prerequisites

- [Node.js](https://nodejs.org/) **22.12 or newer** (the installed Vitest 5 requires 22.12+ or 24+; Vite 8 requires 20.19+ or 22.12+)
- npm (included with Node.js)

### Install

```bash
npm install
```

### Run the development server

```bash
npm run dev
```

Vite prints a local address (usually `http://localhost:5173`). Open it in Chrome or Edge.

### Test, typecheck and build

| Command | What it does |
|---|---|
| `npm test` | Runs all Vitest tests once |
| `npm run typecheck` | Checks TypeScript types without producing files |
| `npm run build` | Typechecks, then creates the production build in `dist/` |
| `npm run preview` | Serves the production build locally (run `npm run build` first) |

## Demo Data

GLORPULSE ships with **four fictional astronauts**, each with **30 simulated mission days**. Each is currently on mission day 30. Every seeded reading is marked as seeded in the code, and each snapshot carries an `isSimulatedData` flag. The Why Now card states that it uses simulated data and prototype rules.

| Astronaut | Role in the demo | Tracks glucose | What to expect at day 30 |
|---|---|---|---|
| **Charl** (`astro-1`) | **Primary story.** Steady for about 25 days, then sleep drops and heart rate rises, with "Tiredness" logged inside the run | No | **Action** alerts on sleep and heart rate |
| **Jelly** (`astro-2`) | Steady profile | Yes | No active alerts |
| **Pond** (`astro-3`) | Missing days (day 3 and day 28) that show the missing-day rule | No | Info alert on heart rate only, because the gap restarted its run |
| **Phuwin** (`astro-4`) | Blood glucose started late, on day 28 | Yes | Glucose shows "building baseline, 3 of 7 days" and no alert |

The names above are the fictional display names used in the code.

**This is not real astronaut medical data.** The numbers were authored to show how the prototype rules behave. They do not represent real physiology.

You can try the app in three ways:

1. Switch astronauts and compare the dashboard, charts and alerts.
2. Open the **Alerts** page for Charl and read a Why Now explanation.
3. Submit a check-in on the **Check-in** page, then use **Reset entered data** in the footer to remove it.

## Safety and Limitations

> **Decision support only. Not a diagnosis or a medical device. It does not replace medical professionals or mission protocols.**

- **Prototype only.** GLORPULSE is a hackathon prototype. It has not been clinically validated.
- **No diagnosis or treatment.** The app never names a disease and gives no medical recommendations of its own.
- **Prototype alert rules are not clinical thresholds.** The 7-day baseline, the median and spread method, K = 3 and the 3-day persistence rule are design choices made for this prototype. They are described as prototype design choices in the Why Now card and in the code, and they are not validated medical limits. The seeded data was written to demonstrate them.
- **A baseline deviation is a statistical comparison**, with the astronaut's own recent readings. It is not a clinical finding.
- **Contact Flight Surgeon is legend-only.** The level is shown in the alert legend with "No automatic trigger in this prototype yet". No rule in the app ever generates it, and no clinical escalation threshold has been invented.
- **No unsourced reference ranges.** No verified general reference range is available, so reference status reads **Not assessed** for every indicator. Where no verified source supports guidance, the app reads **"No sourced guidance available"**.
- **Placeholders.** The symptom list, entry limits, spread floors and the 1 to 5 mood scale are placeholders, not researched clinical content.
- **Fixed mission day.** Every astronaut is on mission day 30 and there is no control to choose or advance the day. A check-in for an indicator replaces that day's reading, so you cannot watch a deviation run grow during a live demo.
- **Frozen baseline.** The baseline comes from the first 7 days and is not updated afterwards. It does not follow long-term adaptation.
- **No sourced guidance yet.** The guidance table is empty, so "why it matters", hazard links and next steps are never shown. The three NASA sources give context only.
- **Test coverage.** Automated tests cover the health logic and data only, with no automated tests of the screens. No formal accessibility or cross-browser testing has been done.
- **English only.**
- **No real data.** No real personal health information is collected, and no health data leaves the browser.

## Data Sources and References

GLORPULSE follows one rule for medical content: **a statement is shown only if it carries a verified source ID, otherwise it reads "No sourced guidance available".** A source counts as verified only after the full document has been read, and only for the specific claims listed for it.

| ID | Source | Verified for |
|---|---|---|
| REF-01 | NASA Human Research Program, [5 Hazards of Human Spaceflight](https://www.nasa.gov/hrp/hazards/) | NASA names five spaceflight hazards |
| REF-02 | NASA, [Space Communications: 7 Things You Need to Know](https://www.nasa.gov/missions/tech-demonstration/space-communications-7-things-you-need-to-know/) | One-way Earth-Mars delay of approximately 4 to 24 minutes |
| REF-03 | NASA Human Research Program, Exploration Medical Capability Element, [EIMO Concept of Operations](https://ntrs.nasa.gov/citations/20240001402) | Mission context: communication delays, with no emergency evacuation or terrestrial medical assistance |

These sources give context only. **None of them provides a reference range, threshold, symptom list or escalation rule**, so the app uses none. The full reading notes, what each source does **not** establish, and open research questions are in [`references.md`](references.md).
